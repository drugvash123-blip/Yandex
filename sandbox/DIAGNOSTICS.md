# Диагностика проекта — 13 октября 2026

## Итог

Проект находится в состоянии рабочего браузерного прототипа с диагностикой.
Поиск через форму Яндекса, пагинация и посещение целевого сайта подтверждены
пятью последовательными живыми прогонами. Полный цикл «задание prstar →
браузер → принятый сервером отчёт» ещё не подтверждён. Полностью автономный
режим сейчас отсутствует: CAPTCHA проходит пользователь.

Эта диагностика основана на текущем коде, Git, локальных тестах и сохранённых
артефактах. Новые обращения к Яндексу, прокси и prstar для неё не выполнялись.
Рабочий вывод относится к проверенному окружению и не гарантирует результат
на других IP, запросах, регионах и вариантах разметки.

## Архитектура и состояние компонентов

| Компонент | Состояние | Доказательства и пределы |
|---|---|---|
| Python + Playwright + установленный Chrome | Работает | Новый main запускает конечный CLI; ChromeDriver не нужен |
| Главная → поле → Enter | Подтверждено | Живые прогоны и локальные сценарии |
| Выдача, домены, пагинация | Работает на проверенной разметке | Точное сравнение hostname/поддоменов, одна позиция на карточку; локально проверено «Показать ещё» |
| Переход на сайт | Подтверждено | Новая/текущая вкладка, поздняя вкладка, видимый body, успешный HTTP-ответ документа |

## Подтверждённая живая серия

Запрос: «мебель из массива сосны». Цель: dms-spb.ru.
Прокси: Webshare 84.247.60.125:6095. На каждом целевом сайте — 100 секунд.

| № | Пауза | Страница/позиция | Результат | Ручная CAPTCHA |
|---|---|---|---|---|
| 1, B | 30 с | 3 / 2 | found, HTTP 200 | Да |
| 2, A | 15 с | 2 / 3 | found, HTTP 200 | Да |
| 3, A | 15 с | 2 / 5 | found, HTTP 200 | Нет |
| 4, A | 15 с | 2 / 7 | found, HTTP 200 | Нет |
| 5, A | 15 с | 2 / 5 | found, HTTP 200 | Нет |

Основной сценарий завершён без ошибок/429 во всех пяти случаях. Это не означает
отсутствие любых сетевых ошибок: были таймауты фоновых запросов Яндекса и отмены
загрузок изображений. Кадр trace подтверждает визуальную отрисовку целевого сайта.
Подробности: AB_TESTS.md и AB_RESULTS.json.

Это ограниченное сравнение, а не статистическая оценка превосходства темпа:
один прогон B против четырёх A, разная глубина нахождения сайта, ручные CAPTCHA
и накопление сессии. Вероятность длительной работы без блокировок не измерена.
Полные пять страниц с отсутствующим доменом допускаются пользователем как успех,
но в этой живой серии все результаты были found; отрицательный случай проверен
локально, не пятью живыми страницами без цели.

## Подтверждённые проблемы и приоритеты

### P1 — Неполный not_found может попасть в отчёт

В runner.search отсутствие элемента пагинации приводит к выходу из цикла и
status=not_found даже до достижения max-pages. completed_search уже отличает
такой случай от полного прогона при определении CLI-успеха. Однако
TaskService.submit принимает любой not_found без проверки полноты. Поэтому
при --upload-stats сервер может получить «Not found» после неполной проверки.

Нужно явно различать «лимит страниц проверен», «выдача достоверно закончилась»
и «управление пагинацией не найдено». В отправку должны попадать только
результаты с достаточным подтверждением проверки.

### P1 — Реальный цикл prstar не проверен

Есть получение и отправка по исходным endpoint, таймауты, запрет редиректов,
сохранение локальных результатов. Но нет подтверждённой реальной задачи и
её принятого отчёта. Сейчас успешный HTTP-код POST считается отправкой;
семантический ответ сервера не валидируется. Поле статистики ip содержит
client_id, а не фактический IP — совместимость с ожиданиями backend нужно
подтвердить. При HTTP-ошибке last_response не сохраняет тело ответа, поскольку
raise_for_status выполняется раньше записи.

Следующий интеграционный тест: реальная тестовая задача prstar, получение,
поиск, ровно одна отправка и подтверждение приёма отчёта на стороне сервера.

### P1 — Новая версия ещё не зафиксирована в Git

runner.py, task_service.py, socks_bridge.py, diagnostics.py, README, зависимости
и sandbox сейчас untracked; main.py изменён. Удаление Data/logs.txt из индекса
подготовлено, .DS_Store уже отслеживается и остаётся изменённым несмотря на ignore.
Другой checkout из текущего commit не воспроизведёт рабочий проект.
Нужно отдельно проверить состав изменений и сохранить версию в Git.
Диагностика сама не создаёт commit и не удаляет файлы.

### P2 — Доказательства готовности выдачи и сайта ограничены

Пагинация ждёт изменения URL или ссылок, затем фиксированную паузу. Изменение
URL ещё не гарантирует, что содержимое обновилось; явной проверки идентичности
новой порции нет. Статусы XHR/fetch-ответов сетью не записываются, если это
не ошибка транспорта, поэтому JSON/SPA-ответ с HTTP 429 может не попасть
в текущую проверку main-document HTTP-статуса.

У целевого сайта проверяются hostname, видимый body и успешный документ;
доступность ключевых элементов сайта и состояние после 100 секунд повторно
не проверяются. HTTP-статус цели не имеет собственного поля Result:
http_status относится к исходной вкладке, а ответ цели проверяется внутри
сценария и восстанавливается из network.jsonl. Нужны отдельный статус цели
и более точное описание этапа/причины отказа.

### P2 — Эксплуатационная устойчивость пока ограничена

Нет очереди неподтверждённых отчётов и механизма продолжения после перезапуска.
Автоматическая повторная отправка сознательно отсутствует; гарантии отсутствия
дубликатов со стороны сервера не проверены. Без явного --profile сессия между
отдельными запусками не сохраняется. Профиль нельзя одновременно открыть
несколькими Chrome. Остаток трафика Webshare не измеряется программой.

Живые проверки охватили один desktop-запрос, один домен и один IP. Мобильный
сценарий, разные регионы, длительная серия и смена IP не подтверждены такой
же серией. CAPTCHA остаётся ручной по согласованному сценарию.

### P2 — Секреты и диагностические данные

Актуальные Data/proxy.json и Data/service-key.txt исключены из Git, имеют
права 0600. Новые сетевые журналы не пишут авторизацию и значения cookies.
Однако legacy-код содержит прежние встроенные реквизиты, Data/key.txt остаётся
отслеживаемым. Ignore и очистка лога не удаляют данные из прежней истории Git.
Перед публикацией репозитория это требует отдельной проверки и устранения.
Сырые HTML/trace могут содержать данные страниц и заголовки; они исключены из Git.

### P3 — Документация и зависимости

README местами устарел: код выхода описан только через found, хотя полная
проверка not_found тоже успешна; есть старые формулировки «backend не проверялся»
и пример профиля прежнего прокси. Ключ доступен и через файл, хотя один абзац
говорит «только BOT_SERVICE_KEY». Основные зависимости заданы диапазонами,
а sandbox lock включает также legacy Selenium/fake-useragent. pytest находится
в общем requirements вместе с runtime-зависимостями.

## Проверки текущей версии

Полный локальный набор актуальных модулей запущен заново:

```sh
.venv/bin/pytest sandbox/test_runner.py sandbox/test_task_service.py sandbox/test_cli.py sandbox/test_socks_bridge.py sandbox/test_diagnostics.py -q
```

Итог: **55 passed in 141.83s**. Тесты используют локальный
HTTP-сервер и установленный Chrome; обращений к prstar/Яндексу не требуется.
Legacy-тесты в эту оценку актуального runner не включены.

## Предлагаемый порядок дальнейшей работы

Обновление после диагностики: первый риск с неполным not_found закрыт
на уровне runner и допуска к отправке. Подробности — PAGE_VALIDATION.md;
64 локальных теста прошли. Реальные короткая/пустая выдачи и полный цикл
с prstar всё ещё требуют отдельного подтверждения.

1. Закрыть различие неполного not_found между runner и отправкой статистики.
2. Провести один реальный полный цикл с тестовой задачей prstar и проверкой приёма.
3. Зафиксировать код, актуальные инструкции и зависимости в Git.
4. Улучшить готовность пагинации, статусы цели и диагностические причины отказа.
5. Затем проверить отрицательную выдачу, другие задания и продолжение после сбоя.

Python/Playwright и последовательный runner для текущего масштаба подходят.
Очереди, параллельные браузеры и дополнительную инфраструктуру сейчас вводить
не требуется: сначала следует подтвердить корректность результатов и backend.
