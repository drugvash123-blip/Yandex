# Yandex browser runner

Инструкция переноса и полного запуска: [DEPLOY.md](DEPLOY.md).

Постоянный режим: `--workers N --proxies-file Data/proxies.json`.
Он восстанавливает исходную схему: параллельные workers перебирают прокси,
получают задания prstar, запускают браузеры и отправляют отчёты в цикле.
Без `--workers` используется конечный runner для одного тестового пакета.

Конечный runner на Python 3.11+ и Playwright. Поиск выполняется в настоящем
Chrome. Внутри одного пакета задания используют общий browser context и cookies.
Без сохраняемого профиля разные пакеты изолированы; в постоянном режиме
каждый прокси использует свой профиль, сохраняющий cookies между пакетами.
Сценарий соответствует исходному проекту: главная `https://ya.ru/` → ввод
запроса в поле → Enter → обработка CAPTCHA → проверка выдачи → переход по
пагинации → клик по найденному сайту → запись результата.
Адрес поиска вручную не конструируется.

## Установка

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

Нужен установленный Google Chrome. ChromeDriver и fake-useragent новому runner
не требуются. Для воспроизведения текущей среды с legacy-тестами используйте
`sandbox/requirements.lock.txt`.

## Одиночный запуск

```sh
.venv/bin/python Source/bots/main.py --query "example domain" --domain example.com --max-pages 2 --deadline 600
```

Переход на найденный сайт включён по умолчанию, как в исходном проекте.
`--no-click` оставляет только проверку позиции. `--headed` показывает окно,
Посимвольный ввод использует исходную паузу 1000 мс между символами
(`--typing-delay-ms` меняет её); таймаут ввода учитывает длину запроса.
`--action-pause` по умолчанию 15 с: перед вводом, перед Enter, перед и после
пагинации и перед кликом по найденному сайту. Перед обработкой каждой выдачи
есть дополнительная пауза минимум 15 с; прокрутка к ссылкам плавная.
При заданном `--captcha-wait` временный 429 можно переждать один раз
до 120 с без повторных запросов runner; после восстановления пауза минимум 30 с.
Повторный 429 останавливает сценарий. CAPTCHA на пагинации обрабатывается автоматически.
`--visit-seconds` по умолчанию
100 с — ожидание на открытом сайте, как в исходном worker. Общий deadline
по умолчанию 600 с учитывает эти паузы и автоматическую CAPTCHA.
`--mobile` включает профиль Pixel 7, `--repeat 2` делает два последовательных
прогона. Без `--domain` runner выбирает случайный органический результат,
сохраняя исходный вариант задания без сайта.
Для автоматического прохождения CAPTCHA:

```sh
.venv/bin/python Source/bots/main.py --query "example domain" --domain example.com --headed --captcha-key-file Data/key.txt --captcha-wait 90 --deadline 600 --click
```

Ожидание CAPTCHA входит в общий deadline; браузер закрывается после завершения.
## Пакет заданий и исходный backend

Локальный JSON-массив заданий содержит `query` и необязательный `domain`:

```sh
.venv/bin/python Source/bots/main.py --tasks-file sandbox/tasks.example.json --proxy-config Data/proxy.json --headed --captcha-wait 180 --deadline 240
```

Пакет конечный, выполняется последовательно; `--limit-tasks` по умолчанию 10.
При неразрешённой CAPTCHA или HTTP 429 следующие задачи/повторы не запускаются.
Результаты уже выполненных заданий остаются на диске.

Восстановлен исходный протокол `prstar.ru`: multipart POST к
`/help/botsSreetsFile` и `/help/botsStatsFile`, `engine=yandex`, строки
`запрос | домен` либо `запрос`. Ключ берётся из `BOT_SERVICE_KEY` или `--service-key-file`.
Получение задания и отправка статистики запускаются явно:

```sh
.venv/bin/python Source/bots/main.py --fetch-tasks --upload-stats --client-id sandbox-test --proxy-config Data/proxy.json --headed --captcha-wait 180 --deadline 240
```

Для стандартного теста без прокси:

```sh
.venv/bin/python Source/bots/main.py --query "мебель из массива сосны" --domain dms-spb.ru --no-proxy --headed --captcha-wait 180 --deadline 600 --max-pages 10 --upload-stats --service-key-file Data/service-key.txt --client-id direct-smoke
```

`--service-key-file` позволяет прочитать ключ из локального файла вместо
`BOT_SERVICE_KEY`; `Data/service-key.txt` исключён из Git.
Отправка отчёта поддерживает как задания сервера, так и ручной запрос/JSON-пакет.
Без `--upload-stats` статистика сохраняется только локально. Для отправки
используются успешные поиски и проверенное отсутствие сайта; CAPTCHA,
неизвестная разметка и сетевые ошибки не превращаются в «Not found».
`client-id` заменяет старое имя файла из строки прокси: учётные данные не
попадают в статистику. Ошибка backend не удаляет локальные результаты.
Один проход получения заданий, без бесконечного цикла и автоматического повтора
сетевых записей. Реальный backend проверен на пустом получении и отправке двух
результатов: HTTP 200 с пустым телом. Сохранение записей на сервере пока не
подтверждено. Контракт также протестирован на локальном HTTP-сервере;
подробности — `sandbox/PRSTAR_API_TESTS.md`.

## Ручной тест обычного Chrome

Для контрольного ручного поиска используется отдельный launcher, который
запускает установленный Chrome обычным процессом, не подключая Playwright
или удалённую отладку. Начальная страница локальная и показывает фактические
параметры браузера; Яндекс открывает пользователь.

```sh
.venv/bin/python sandbox/native_manual_browser.py --proxy-config Data/proxy.json --profile Data/browser-profiles/native-socks195
```

Название начальной вкладки: «Ручной тест — обычный Chrome». В проверенном запуске
`navigator.webdriver=false`, язык `en-GB`, часовой пояс `Europe/Moscow`.
Это не подмена navigator в автоматизированном браузере. Значения записываются
в `sandbox/artifacts/native-manual-*/environment.json`. Поисковые запросы
и отчёты этот launcher не отправляет; браузер не закрывается по таймеру.
Язык и профиль отличаются от Playwright-сценария, поэтому успешный/неуспешный
контроль сам по себе не доказывает одну конкретную причину HTTP 429.

Мост SOCKS5 поддерживает обычный HTTP (включая начальный GET http://ya.ru/)
и HTTPS через CONNECT. Chunked-тело обычного HTTP не поддерживается; для HTTPS
туннель передаёт поток без разбора тела. Неиспользуемое входящее соединение
закрывается без искусственного ответа 502.

## Сессия и диагностика

`--profile Data/browser-profiles/socks195` сохраняет отдельный профиль runner:
постоянные cookies и localStorage остаются между запусками. Обычный пользовательский
профиль Chrome не используется. Один профиль привязан к адресу прокси,
пользователю прокси, браузеру и мобильному режиму; для другой конфигурации нужен
другой каталог. Один каталог нельзя открывать одновременно в нескольких Chrome.
Профиль и cookies не отправляются на prstar. Сохранение сессии само по себе не
доказывает и не устраняет причину HTTP 429.

Для будущей контролируемой проверки (команда пока не запускалась на Яндексе):

```sh
.venv/bin/python Source/bots/main.py --query "мебель из массива сосны" --domain dms-spb.ru --proxy-config Data/proxy.json --profile Data/browser-profiles/socks195 --headed --keep-open-on-failure --captcha-wait 900 --deadline 1800
```

В каталоге каждого прогона:

- `network.jsonl` — запросы навигации, ответы, цепочки перенаправлений и ошибки.
  Без заголовков, тела запросов, значений cookies, URL-учётных данных и лишних
  параметров URL; остаются только `text`, `p`, `lr`.
- `session.json` — ID сессии, профиль, настроенный прокси без авторизации,
  версия браузера, количество cookies и фактические User-Agent, webdriver,
  язык, платформа, часовой пояс. Эти настройки не подменяются.
- `batch-error-*.json` — ошибка запуска браузера или пакета с безопасным кодом,
  например `net::ERR_TIMED_OUT`, вместо прежнего неинформативного `Error`.

С `--keep-open-on-failure` вкладка получает название **Runner — ручная проверка**.
После остановки сценария запись продолжается в `inspection-network.jsonl`;
можно вручную открыть главную и отправить тот же запрос в той же сессии.
Результат исходного прогона не меняется и новый отчёт автоматически не отправляется.
Закройте это окно вручную после проверки. Ошибка маркировки вкладки не закрывает
браузер. Этот режим применяется только к будущим запускам, а не к старым окнам.

Обычные HTML, скриншоты и trace остаются исходными и могут содержать данные
страниц и заголовки; они, как и тестовые профили, исключены из Git.

## Прокси

`--no-proxy` игнорирует переменные прокси и запускает Chrome с `--no-proxy-server`.
Прокси задаётся через `BROWSER_PROXY_SERVER` (например `http://host:port`),
`BROWSER_PROXY_USERNAME`, `BROWSER_PROXY_PASSWORD`. Значения не печатаются.
Ротация и расширения не нужны для одиночного smoke.
Для SOCKS5 с авторизацией runner автоматически запускает локальный CONNECT-мост
на 127.0.0.1 и останавливает его после прогона: Chrome не поддерживает SOCKS5 auth.
Соединение SOCKS5 ограничено 45 с, навигация браузера — 60 с.
Можно использовать `--proxy-config Data/proxy.json` с JSON-полями `server`
(`http://host:port` для HTTP CONNECT или `socks5://host:port`), `username`, `password`. Этот файл исключён из Git.
Проверка SOCKS5 и моста: `.venv/bin/python sandbox/proxy_probe.py Data/proxy.json`.

В `sandbox/artifacts/<run-id>/` сохраняются `result.json`, `page.html`, `page.png`,
`trace.zip`; общий журнал — `sandbox/artifacts/results.jsonl`.
Каждый шаг записывается с временем в поле `actions`; список результатов и
снимок каждой просмотренной страницы — в `results-N.json/html/png`.
Ответ backend при отправке сохраняется в `submission-<id>.json`, включая
HTTP-статус и тело ответа. Для результатов, не пригодных к отправке,
записывается `submitted=false`, без сетевой отправки статистики.
Результат `found` означает найденный домен, а при `--click` — также проверенный
переход. Другие статусы: `not_found`, `captcha`, `unexpected_page`,
`navigation_failed`, `submission_failed`, `pagination_stalled`, `timeout`, `error`.
`navigation_timeout` означает, что страница поиска не успела загрузиться.
Если при этом CAPTCHA уже открыта, runner продолжает ручное ожидание.
Также выделяются `rate_limited` для временной блокировки IP/HTTP 429 и
`http_error` для остальных HTTP ошибок поиска. При `rate_limited` batch
останавливается без следующих повторов. Поле `http_status` хранит статус
документа выдачи. Код выхода 0 только если все прогоны
получили `found` либо подтверждённый `not_found`; иначе 1. Статусы CAPTCHA и неизвестной разметки не считаются
отсутствием сайта. Позиция — номер органического результата (одна ссылка на карточку).
При обычной пагинации она считается на странице; при «Показать ещё» — в
накопленном списке. Поле `pagination` различает эти режимы, `pages_checked`
считает просмотренные страницы/порции, `stage` показывает этап завершения.
Для найденного сайта сохраняется также `search.html`/`search.png` перед кликом;
`page.html`/`page.png` показывают конечную страницу.

Таймаут задачи ограничивает браузерный сценарий. Запись диагностики и закрытие
ресурсов имеют отдельные короткие таймауты и могут увеличить время завершения.
Браузер запускается один раз на пакет и закрывается после него; после посещения
сайта лишняя вкладка закрывается, основная вкладка и cookies сохраняются.
Артефакты могут содержать данные посещённой страницы, поэтому они исключены из Git.

## Достоверность проверки выдачи

Для каждой обработанной страницы сохраняется `page_checks`: номер, совпадение
запроса, количество органических результатов и их URL. Адрес должен содержать
тот же `text`; при обычной пагинации `p` должен соответствовать номеру страницы.
Повтор того же набора сайтов не засчитывается как новая страница.
Изменение URL само по себе больше не завершает ожидание обновления результатов.

`search_complete` и `completion_reason` объясняют завершение:

- `target_found`: целевой результат найден;
- `page_limit`: проверен заданный лимит страниц;
- `end_of_results`: распознана последняя страница по текущему номеру и состоянию pager.

Короткая выдача с подтверждённым концом — нормальный `not_found`. Если переход
дальше отсутствует, но конец не подтверждён, результат — `incomplete`, а не
отсутствие сайта. Такой результат не отправляется в prstar. Старые `not_found`
без подтверждающих полей тоже не отправляются автоматически.

Отсутствие любых карточек пока само по себе не доказывает пустую выдачу:
незнакомый вариант возвращает `unexpected_page`. Устойчивость к изменению
разметки и ограничения распознавания описаны в `sandbox/SELECTOR_RISKS.md`.

## CAPTCHA: локальная подготовка

Ручное ожидание CAPTCHA удалено. Платный адаптер включается
явным `--captcha-key-file Data/key.txt`; в постоянном режиме ключ обязателен.
По умолчанию число отправок не ограничено. `--captcha-max-tasks N` задаёт
общий предел; `0` снимает лимит числа платных задач, сохраняя тайм-аут поиска.
Следующий этап оплачивается только после наблюдаемой смены
задания; ошибка транспорта или формата не запускает новую отправку. `--captcha-kinds text|silhouette|both`
ограничивает формат. Ошибка транспорта или неподдерживаемый вид
завершают задание с ошибкой и диагностикой, без участия человека.
Один и тот же запрос создания не повторяется; временный
обрыв при получении ответа повторяет чтение по сохранённому номеру задачи.

Живой обмен CapGuru для текста проверен, но демо после ответа потребовало
дополнительную проверку. Полный автоматический успех пока не подтверждён:
платный режим остаётся экспериментальным. Транспорт использует HTTPS,
метаданные запросов сохраняются без ключа и ответа распознавания.

Слайдер распознаётся диагностикой и остаётся для ручного прохождения в новом
runner. Старый алгоритм сохранён в legacy Bot; живого подтверждения его
совместимости с актуальной страницей нет. Он не удалён и автоматически не
подключается вместо неподдерживаемого современного варианта.

Локальные тесты не вызывают платный API:

```sh
.venv/bin/pytest sandbox/test_captcha_service.py sandbox/test_captcha_browser.py -q
```

Текст, координаты, смена картинки и отказ подтверждения проверяются на локальной
странице с отключённой сетью. Подробности — sandbox/CAPTCHA_REVIEW.md.
Data/key.txt теперь исключён из новых коммитов; legacy botsKey читается из
BOT_SERVICE_KEY или локального Data/service-key.txt вместо встроенного значения.
Удаление ключей из текущей версии не очищает старую историю Git.

## Проверки

```sh
.venv/bin/python -m pytest sandbox/test_runner.py sandbox/test_task_service.py sandbox/test_cli.py sandbox/test_socks_bridge.py sandbox/test_diagnostics.py -q
```

Локальный HTTP fixture проверяет фактический путь через главную и форму,
переходы по кнопкам страниц и «Показать ещё», одну позицию на карточку,
текущую/новую вкладку, задания без домена, отсутствие сайта, CAPTCHA и deadline.
Проверки CLI подтверждают порядок задач и остановку при CAPTCHA; отдельный
сервер проверяет исходный multipart-протокол и обработку ошибок статистики. Chrome запускается
реально; proxy/backend/CAPTCHA сервисы не вызываются.

Старый бесконечный main сохранён в `Source/legacy/main.py` как исторический
исходник, не самостоятельная точка запуска. Остальные Selenium-модули оставлены
для сравнения; новый main их не импортирует. Старые регрессионные проверки
`sandbox/test_legacy.py` продолжают фиксировать известные дефекты legacy-кода.

## Ожидание задания от сервера

`--fetch-tasks --wait-for-tasks 3600 --task-poll-interval 60` ждёт первый
непустой пакет до часа. Минимальная пауза между запросами — 30 секунд.
Чтобы проверить один полный цикл, добавьте `--limit-tasks 1 --upload-stats`,
явный `--client-id` и файл ключа prstar. При истечении ожидания без задания
код выхода — 2, браузер не запускается и отчёт не отправляется.
Журнал `runner.log` в каталоге `--output` содержит количество задач,
HTTP-статусы и длины ответов. Записи отчётов отправляются один раз;
HTTP 200 с пустым телом не заменяет проверку сохранения в prstar.

Полученные серверные задачи сохраняются в received-tasks.json до открытия
браузера, чтобы прерывание запуска не теряло исходные данные задания.
